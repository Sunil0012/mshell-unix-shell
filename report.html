Abstract

MShell is an educational command interpreter written in C for Linux/POSIX environments. It launches external programs with fork and execvp, connects commands with pipes, redirects standard input/output/error, and manages foreground and background jobs using process groups and signals. It includes a deliberately limited scripting layer, persistent command history, timestamped command traces, glob expansion, and process tracing.

The project is evaluated with automated functional checks, a pseudo-terminal job-control test, a small compatibility comparison against Bash, and a repeated process-launch benchmark. The report documents both demonstrated behavior and known limitations; MShell is not presented as a complete POSIX or Bash implementation.

1. Objectives and scope

  • Apply operating-system process APIs to launch and supervise programs.
  • Demonstrate IPC and descriptor duplication through pipelines and redirection.
  • Implement terminal foreground/background control using process groups and signals.
  • Provide a reproducible test suite, trace mode, and performance comparison.
  • Define a manageable Unix-style shell subset instead of claiming full shell compatibility.

2. Architecture

The implementation follows a read–parse–execute loop. Input is split into command segments, tokenized with quote and escape handling, expanded, and parsed into a pipeline. Each pipeline stage is represented by a command with an argument vector and optional redirection paths.

3. Process creation and pipeline execution

For an N-stage pipeline, the parent creates N−1 pipes and forks one child per command. A child joins the common process group, duplicates the previous pipe's read end onto standard input and the next pipe's write end onto standard output, applies explicit redirections, then executes the program. The parent closes pipe descriptors it no longer needs and waits for the process group when the pipeline is foregrounded.

producer | filter | consumer
pipe() → fork producer → fork filter → fork consumer
             dup2(write)   dup2(read/write)  dup2(read)
parent: close unused ends → transfer terminal → wait for process group

External programs are resolved through PATH. Builtins that change shell state, such as cd and variable assignment, execute in the shell process when used alone; a builtin in a pipeline runs in a child and therefore cannot change the parent shell state.

4. Job control and signals

In interactive mode, the shell establishes its own process group, takes terminal foreground ownership, and ignores terminal-control signals that should not stop the shell. Children restore default signal dispositions. A foreground job receives terminal ownership while it runs; after completion or suspension, the shell reclaims the terminal.

Ctrl-C produces SIGINT for the foreground process group. Ctrl-Z produces SIGTSTP. The shell records each pipeline child and updates the job state from waitpid events, enabling jobs, fg, and bg. PTY integration tests exercise stop, list, resume in background, foreground resume, and interrupt across a two-process pipeline.

Grammar constraints: script blocks do not nest; functions have no positional parameters; aliases expand a command name to one word. Command substitution and the complete POSIX/Bash grammar are not implemented.

6. Validation strategy and results

Run make test from the repository root. The target builds MShell and executes three layers of checks:

  1. Smoke checks cover command lists/status, pipelines, globbing, stderr redirection, heredocs, aliases, sourcing, script control flow, and trace output.
  2. A Bash compatibility check compares output for a small shared subset. It is a targeted check, not a conformance suite.
  3. A Python pseudo-terminal test interacts with the real terminal interface to exercise Ctrl-Z, jobs, bg, fg, and Ctrl-C for a pipeline.

All three test stages passed in the development environment. Compiler warnings about compressed one-line control statements remain; they are readability warnings and should be cleaned up in a future maintenance pass.

7. Benchmark methodology

The comparison workload executes external /bin/true repeatedly. Each shell processes the same generated input. The Python driver performs one warm-up per shell, alternates measured run order to reduce order bias, measures elapsed time with a monotonic clock, and reports each shell's median, interquartile range, minimum, and maximum. It also calculates paired differences between corresponding alternating runs and writes raw data to CSV.

The recorded 25-run, 3,000-command trial produced the following summary (values supplied from the benchmark run):

The difference of medians is +0.0318 s, approximately 2.0% of Bash's median. The ranges overlap and the MShell maximum reflects a slower run; the result supports only a modest observed difference for this workload. Since process creation and waiting dominate this benchmark, it does not measure shell parsing, pipelines, redirection, or job-control performance. Results depend on hardware, kernel, compiler, and system load; the test should be repeated on an identified host before drawing broader conclusions.

8. Reproduction and demonstration

make
make test
sh benchmarks/compare.sh --commands 3000 --runs 25 --csv results.csv
./run-mshell.sh
# in the interactive shell:
source demo.ms

The demo shows a pipeline, file redirection, a background job, job listing, and foregrounding. Use Ctrl-C to stop the foreground sleep, or Ctrl-Z followed by bg/fg to demonstrate suspension and resumption.

9. Limitations and future work

  • Expand the parser into a structured grammar with nested blocks and positional function parameters.
  • Add more complete quoting rules, command substitution, and standard shell expansion behavior.
  • Test additional pipeline failure cases and terminal modes across Linux terminal emulators.
  • Refactor compressed C statements, add memory/error-path cleanup, and run sanitizers.
  • Record CPU, kernel, compiler, and load details for benchmark reproducibility.

Conclusion

MShell demonstrates core operating-systems mechanisms in an inspectable C project: process creation, execution replacement, descriptor duplication, IPC, process groups, signals, and terminal job control. A layered test suite, trace mode, Bash subset comparison, and repeated benchmark make its behavior easier to evaluate. Its deliberately limited grammar and measured-performance scope are stated so the work can be assessed on its actual implementation.
