CSL301 · OPERATING SYSTEMS PROJECT OVERVIEW
01 · EXECUTIVE SUMMARY

Abstract and objectives

MShell is an educational command interpreter written in C for Linux/POSIX environments. It launches programs with fork and execvp, connects commands through pipes, redirects standard streams, and controls foreground/background jobs with process groups and signals. Supporting features include environment expansion, globbing, heredocs, aliases, sourceable scripts, history, tracing, and limited script control flow.

The project is evaluated through automated tests, pseudo-terminal job-control checks, a Bash comparison for a small shared subset, and a repeated process-launch benchmark. MShell is not a complete Bash or POSIX shell.

Objectives

  1. Demonstrate process creation and image replacement.
  2. Implement descriptor routing and pipelines.
  3. Manage terminal ownership and process-group job states.
  4. Provide reproducible tests and measured results.
Project framing
A bounded Unix-style shell subset, with source code, tests, and evidence for its behavior.

Research questions

  • How does a shell connect separately executing processes into a pipeline?
  • How does terminal ownership change between shell and foreground job?
  • What does a repeated external process-launch workload reveal about relative overhead?

02 · KERNEL INTERFACES

Operating-system mechanisms

The shell is a user-space coordinator. It asks the kernel to create processes, connect descriptors, deliver signals, and report process-state changes. The kernel—not MShell—performs CPU scheduling.

APIRole in MShellConcept
fork()Create one child per pipeline stage.Process creation
execvp()Replace child image with selected program.Program execution
pipe()Connect producer to consumer.IPC
dup2()Route pipe/file descriptors to standard streams.Descriptor tables
setpgid()Place children in a job group.Process groups
waitpid()Observe exit, stop, and continue events.Process state
tcsetpgrp()Transfer terminal foreground ownership.Terminal control

Process lifecycle

parse → fork → configure process group and descriptors → exec → waitpid → update job
A pipeline contains multiple processes but is managed as one process-group job, allowing terminal signals to target all its children.

State-changing builtins such as cd and variable assignment run in the parent shell when used alone. A builtin inside a pipeline runs in a child, so it cannot change the parent shell state.

Descriptor lifetime

Unused descriptors must be closed in both parent and children. Otherwise a reader can wait indefinitely because a write end remains open. Correct pipeline behavior depends on descriptor lifetime as much as on calling pipe().

CSL301 · OPERATING SYSTEMS PIPELINES & REDIRECTION
05 · DATA FLOW

File descriptors and pipelines

For an N-stage pipeline, the parent creates N−1 pipes. Each child maps relevant pipe ends to standard input/output with dup2, applies explicit redirections, closes unused descriptors, then executes. The parent closes its copies so readers can observe EOF when writers finish.

OperatorStreamBehavior
< filestdin (0)Read-only
> filestdout (1)Create/truncate
>> filestdout (1)Create/append
2> filestderr (2)Create/truncate
2>> filestderr (2)Create/append
<< ENDstdin (0)Read through delimiter

Example descriptor map

cat input | grep error > matches 2> errors
cat stdout → pipe → grep stdin
grep stdout → matches
grep stderr → errors

Redirection happens in children, preserving the shell's own streams. Open and duplication failures are reported by the affected process.

CSL301 · OPERATING SYSTEMS JOB CONTROL
06 · PROCESS GROUPS

Foreground and background jobs

Interactive startup places the shell in its own process group and gives it terminal foreground ownership. Pipeline children join a shared process group. While foregrounded, the job owns the terminal and the shell waits for child-state events. When the job stops or completes, the shell reclaims terminal control.

Integration check

The PTY test launches a two-command pipeline, sends Ctrl-Z, checks the job listing, resumes it in the background and foreground, then sends Ctrl-C. This exercises terminal-generated signals, not merely builtin parsing.

CSL301 · OPERATING SYSTEMS SCRIPTING & TRACE
07 · SHELL STATE

Builtins, history, and observability

Builtins and state

cd, pwd, export, and unset manage shell state. jobs, fg, and bg operate on the job table. alias/unalias define simple command-name shortcuts; source executes a file in the current shell.

Persistent command records

Submitted input is appended to ~/.mshell_history and timestamped in ~/.mshell_trace.log. The history builtin lists earlier commands. Both records are plain text in the user's home directory.

Process tracing

./mshell --trace script.ms prints application-level launch metadata to stderr:

[trace] fork stage=1/2 command=cat
[trace] pid=24110 pgid=24110
[trace] fork stage=2/2 command=grep
[trace] pid=24111 pgid=24110

Each pipeline stage has a distinct PID while both share the pipeline PGID. This is an educational diagnostic, not a kernel event trace.

Demo: launch ./run-mshell.sh, then enter source demo.ms to see a pipeline, redirection, background job, job listing, and foregrounding.

Benchmark method

Each run launches external /bin/true 3,000 times. The driver warms up each shell, alternates order, and measures elapsed time with a monotonic clock. The 25-run summary supplied for this report:

ShellMedianIQRMinMax
MShell1.6134 s0.0272 s1.5821 s1.7849 s
Bash1.5816 s0.0502 s1.5189 s1.7042 s
MShell · 1.6134 s
Bash · 1.5816 s

Difference of medians: +0.0318 s, about 2.0% of Bash's median. The ranges overlap, and one MShell run was slower. This is a modest observation for process launching, not a general performance claim. Host model and kernel details were not recorded.

CSL301 · OPERATING SYSTEMS CONCLUSION & REFERENCES · 10 / 10
09 · ASSESSMENT

Findings and future work

Demonstrated

  • Fork/exec lifecycle and parent-child coordination.
  • Descriptor routing, IPC pipes, and stream redirection.
  • Process groups, terminal ownership, signal delivery, and job control.
  • Behavioral tests, Bash subset comparison, and PTY integration.
  • Repeated, workload-specific performance measurement.

Limitations

  • Not a full POSIX/Bash grammar; command substitution is absent.
  • Script blocks cannot nest; functions take no positional parameters.
  • Aliases expand one command word.
  • Benchmark results depend on machine, kernel, compiler, and system load.

Future work

  1. Use a structured parser for nested blocks and function parameters.
  2. Expand compatibility checks for quoting, errors, and redirect ordering.
  3. Run sanitizers and improve cleanup on all error paths.
  4. Record host and compiler metadata with benchmark samples.
Reproduce: make test
sh benchmarks/compare.sh --commands 3000 --runs 25 --csv results.csv

Conclusion

MShell connects OS mechanisms to a practical command interface. Its source and tests demonstrate process creation, execution replacement, IPC, descriptor duplication, process groups, signals, and terminal job control. The report states compatibility and measurement limits so the project can be evaluated against its actual implementation.
